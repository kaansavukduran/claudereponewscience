# Decisions

## ADR-IMPL-002: Flutter for the five product surfaces; TypeScript kept as reference oracle and Build Lab (2026-10-06, ACCEPTED)

**Context.** The user's master prompt and the v0.24/v0.27 handoffs prefer one Flutter/Dart client for Android, iOS, Web/PWA, Windows (portable and installer) and macOS. ADR-IMPL-001 chose TypeScript only because Flutter was not installed at the time. That decision was never accepted by the user. Flutter 3.47.6 can now be installed in this container (storage.googleapis.com and pub.dev are reachable).

**Decision.**
1. `human_health_os/` (Flutter, created with `flutter create --empty --platforms=android,ios,web,windows,macos,linux`) is the product for all five surfaces.
2. The domain core is pure Dart in `lib/src/domain`, ported engine by engine. Each engine must pass the same `contracts/golden_vectors`.
3. `packages/domain` (TS) remains the reference oracle (differential testing). `apps/site` remains the **Build Lab** (synthetic, separate). `services/api` remains the reference for sync semantics. `apps/client` is frozen and retired at parity.

**Alternatives considered.** (a) TypeScript everywhere (Capacitor + Tauri/Electron). It keeps one runtime core, but it goes against the explicit Flutter preference and the Windows-portable expectations, and it adds a third desktop runtime. (b) Flutter for everything, rebuilding the Build Lab now. That throws away a tested, working Lab and its cross-language parity checks for no user value.

**Consequences.** There are two implementations of each engine, held together only by vectors. Composites, compare and missions need numeric vectors **before** they are ported (gap G-07). Reversible: no code is deleted.

## D-007: Dependency policy

## D-008: Linux is a first-class product surface (user instruction, 2026-10-06)

The user added: "Linux version too: it must work on Nobara/Fedora derivatives and on Ubuntu/Debian derivatives." Linux is therefore the **sixth primary surface**, not a CI-only smoke target. It uses the same Flutter app, the same vault rules (XDG data dir, or `UserData/` in portable mode) and the same honesty rules.

- **Compatibility floor:** the bundle built in FORGE 001 requires at most `GLIBC_2.34` (checked with `objdump -T`), plus GTK 3, libepoxy and libstdc++. That covers Fedora ≥ 35 / Nobara, Ubuntu ≥ 22.04, Debian ≥ 12 and their derivatives. Debian 11 and Ubuntu 20.04 (glibc 2.31) are **not** covered unless release builds move to an older-glibc builder. Release builds should run on the oldest supported base (Ubuntu 22.04 runner) so the floor does not drift upward.
- **Distribution formats** (each verified independently on real distros before it counts as PASS):
  1. Portable `HumanHealthOS-Linux-x64-Portable.tar.gz`: bundle + `portable_mode.json` + `UserData/` (the Rufus-like experience).
  2. AppImage: one-file portable that runs across distros.
  3. `.deb` for Ubuntu/Debian.
  4. `.rpm` for Fedora/Nobara.
  5. Flatpak (Flathub-ready manifest), which suits Fedora/Nobara users.
- **Testing:** the build-and-launch smoke runs here on Ubuntu 24.04. Fedora/Nobara and Debian launch tests need containers or VMs (`fedora:latest`, `debian:12`, `ubuntu:22.04`) in CI. They stay NOT_RUN until executed.

## D-009: Linux distribution layer aligned with the v0.28 candidate report (2026-10-06)

The user shared the v0.28 Forge report. Its Linux design is adopted on top of D-008:

- **Channels:** Flatpak is the primary cross-distro install channel. The AppImage `HumanHealthOS-x86_64.AppImage` is the Rufus-like portable option. Because of AppImage's FUSE dependency it is never the only channel; `--appimage-extract-and-run` is the documented fallback. The portable fallback `HumanHealthOS-Linux-x86_64-Portable.tar.zst` carries the real Flutter `bundle/`. Native packages: `human-health-os_<version>_amd64.deb` (Ubuntu/Debian) and `human-health-os-<version>-1.x86_64.rpm` (Fedora/Nobara). Snap is optional. ARM64 is planned and is not PASS without a real toolchain and runtime test.
- **Test matrix:** Ubuntu 22.04 and 24.04, Debian 12 and 13, Fedora 44, Nobara 44 (Official/KDE and GNOME). Sessions: GNOME + Wayland, KDE + Wayland, and X11 where supported. A Wayland bug is never "fixed" by forcing the whole app onto X11. Fedora PASS does **not** count as Nobara PASS. Mint, Pop!_OS, Zorin, elementary, KDE neon, Arch, EndeavourOS, Manjaro and openSUSE are in the broad-compatibility tier. Being in the same family ≠ tested compatibility.
- **Data on Linux:** `XDG_DATA_HOME` (vault), `XDG_CONFIG_HOME` (settings) and `XDG_CACHE_HOME` (disposable cache). Keys use a Secret Service/keyring adapter. If no keyring exists, **writing a plaintext key is forbidden**; the passphrase-only vault path is used instead. Portable Linux uses the same encrypted vault rules as portable Windows.

**Correction this repo adds (evidence-based).** The report cites Flutter's support matrix (Debian 10–13, Ubuntu 20.04–24.04). Upstream support does not make *our* binary run there. The bundle built in FORGE 001 on Ubuntu 24.04 needs `GLIBC_2.34` (measured with `objdump -T`). Debian 10 (glibc 2.28), Debian 11 and Ubuntu 20.04 (glibc 2.31) would fail to start the native `.deb`, `tar.zst` or AppImage builds. To cover them, the release builder must run on the oldest targeted glibc (for example a Debian 10 or 11 build container), or those versions are dropped from the native-package matrix. Flatpak is unaffected because its runtime ships its own glibc. Until that builder exists, the native-package floor is glibc 2.34: Fedora ≥ 35/Nobara, Ubuntu ≥ 22.04, Debian ≥ 12.

## D-016: Dependency review — `pointycastle`, and the vault cryptography (F006, 2026-10-07; D-007 procedure)

- **Package:** `pointycastle` 4.0.0, pinned exactly (pub.dev, verified publisher `bouncycastle.org`, repository `github.com/bcgit/pc-dart`, latest release 2025-02-19, checked 2026-10-07). Transitive: `convert` 3.1.2 (dart.dev); `collection` was already present.
- **Purpose:** Argon2id key derivation and ChaCha20-Poly1305 authenticated encryption for the encrypted vault and its backups. No other part of the library is used.
- **License:** MIT (The Legion of the Bouncy Castle), OSI approved.
- **Maintenance:** port of Bouncy Castle; pub points 140/160; about 3.9 M downloads in 30 days; null-safe, Dart 3; no native code, no network use.
- **Correctness evidence, kept in the test suite** (`test/data/vault_crypto_test.dart`): RFC 8439 §2.8.2 (seal and open), RFC 9106 §5.3 (Argon2id), and two vectors computed with the Argon2 reference C implementation (argon2-cffi 23, independent of pointycastle) for the app's exact parameters and UTF-8 encoding, one with Turkish letters.
- **Platforms:** native (Dart VM/AOT) on Android, iOS, Linux, macOS and Windows. **Not usable under dart2js**, measured 2026-10-07 in V8 (Node 22): `Poly1305` throws "full width integer not supported on this platform", and Argon2id at the vault cost takes 7.4 s (0.25 s native). pub.dev's `platform:web` tag does not hold for this use. Web builds other than development therefore keep data in memory (G-32). Routes for later: dart2wasm (64-bit integers; pointycastle declares wasm support since 3.8.0), or WebCrypto (AES-GCM, PBKDF2) behind the same envelope with another `aead` value.
- **Parameters:** Argon2id v1.3, m = 19 MiB, t = 2, p = 1 (OWASP Password Storage Cheat Sheet minimum), a 16-byte random salt per wrapped key, stored next to it; parameters read from a file are refused outside fixed limits. ChaCha20-Poly1305, 256-bit key, 96-bit random nonce per sealed line (`Random.secure()`), 128-bit tag. Key derivation runs in an isolate on native builds.
- **Alternatives:** `cryptography` (more moving parts, platform plugins with native code); libsodium through FFI (a native build per platform, no web); AES-256-GCM in pure Dart (measured about 23 times slower than ChaCha20 natively; the candidate for WebCrypto interop later). OS key stores (Keychain, Keystore, DPAPI, Secret Service) may only ever be a convenience unlock (master §11) and are not built (G-13).
- **Design decisions taken with it:**
  1. Envelope `hhos-vault-enc` v1 seals each line of the unchanged logical log (vault format 1), so replay rules, migrations and fixtures stay the same; associated data binds every sealed line to its vault id and sequence number.
  2. A random 256-bit data key; a passphrase slot and a recovery slot wrap it; no key is ever stored unwrapped; the recovery key (160 random bits) is shown once and must be confirmed before the vault exists.
  3. Setting a new passphrase (after a recovery) rewrites only line 1, atomically; sealed lines stay byte for byte. Copies made earlier still open with the old passphrase (G-33).
  4. Development builds keep the labelled plaintext log. Staging, production and portable desktop builds persist only through the encrypted vault, and write nothing before it is created; staging and production use different files (`vault-staging.hhosvault`, `vault.hhosvault`), so a mislabelled build never opens production data.
  5. A failed unlock writes nothing and never opens a plaintext store. "Start a new vault" (key lost, or a damaged file) renames the old file; nothing is deleted. A vault written by a newer app is never set aside.
  6. Encrypted backups carry the envelope byte for byte; restoring one asks for the backup's own passphrase or recovery key and checks the content before anything is written; plaintext and encrypted backups never cross. Export (plaintext JSON) is not offered for encrypted vaults (G-34).
- **Lockfile:** `human_health_os/pubspec.lock` is committed with the change.

## D-018: Measurements — kinds, units, structured blood pressure, record schema 4 (F007@v0.32 slice 1, 2026-10-09)

- **Kinds and units (canonical, no conversion):** `body.waist_circumference` (cm), `vital.resting_heart_rate` (bpm), `vital.blood_pressure` (mmHg). Any other unit is refused (`UNIT_NOT_SUPPORTED`): no conversion rule exists, so none is invented (v0.24:19390).
- **Mapping from v0.24 VitalMeasurement / BloodPressureMeasurement** (v0.24:2566-2585) to the envelope: `user_id` → `profile_id`; `metric` → `kind`; `value`, `unit` → `quantity` (waist, heart rate); `measured_at` → `observed_at`; `device_or_source` → `provenance`; `corrects_id` → `supersedes_id` + `amend_reason`; `context` → optional free text `context` (as typed, at most 500 characters, measurement kinds only). v0.24 gives BloodPressureMeasurement no `corrects_id`, while its module lists "create correction" (v0.24:23802-23805) and FR-22 asks for correction provenance (v0.24:840-841): the envelope lineage applies to every kind (docs/DATA_MODEL.md), recorded in SOURCES.
- **Blood pressure is one record with two numbers.** Its value lives in a kind-tagged `details` slot (`{type: "blood_pressure", systolic, diastolic, unit, systolic_text, diastolic_text}`), never in `quantity` (`BP_HAS_NO_QUANTITY`): a generic consumer must not show one number as "the" reading. Later structured kinds add a `details` subtype, not a new JSON key. A present reading needs its details (`DETAILS_MISMATCH`); a not-measured entry carries neither number nor details.
- **Validation is structural, never clinical.** Numbers are finite; waist, heart rate and systolic are above 0; a stored diastolic may be 0 (sounds heard down to zero), typed entry refuses 0 (leave the field empty). There is no upper bound and no REVIEW tier: no sourced, versioned rule set exists (master:2709; G-46). The order rule (systolic above diastolic, `BP_ORDER`) is **an entry rule only**, so domain rules only loosen over time and a stored record is never re-judged.
- **State and provenance:** a hand-typed measurement is `OBSERVED` with `Provenance.manual` (v0.24:3054-3056 status semantics; v0.24:19337 USER_ENTERED), unlike a lab value, which is transcribed from a report (`REPORTED`, F004). `observed_at` is the time Save is pressed (said on screen; G-44). Nothing is derived, averaged, categorised or judged. Two identical readings seconds apart are two records; only a same-id retry is idempotent (v0.24:14135-14137).
- **Record schema 4 (RS-004), additive.** The three kinds and the keys `context` and `details` exist only at schema 4 (`KIND_NEEDS_NEWER_SCHEMA`, `FIELD_NEEDS_NEWER_SCHEMA`, checked before the marker early return). Records of schema 1–3 keep their exact JSON. The reader accepts schemas 1–4 and refuses 5. **Each record is written with the oldest schema that holds it** (`writeSchemaFor`): weight and lab results are still written at 3, measurements and their markers at 4. Older apps are therefore locked out (`RECORD_SCHEMA_NEWER`) only once a measurement is saved. No vault-format or envelope change, no on-disk rewrite; `migration_ids` is `["RS-004"]`, an identity for the additive change (conflict C-10 with master §35.1).
- **Upgrade checkpoint:** before the first record whose schema exceeds every stored schema in a non-empty vault, a backup of the vault as it is goes to `backups/` (plaintext in development, the encrypted envelope otherwise) and its place is named on screen. If it cannot be written the save is refused (`CHECKPOINT_FAILED`) and nothing is stored. Browser builds cannot save a file unasked and keep none (G-47).
- **Correction guards:** every `correct*` method refuses a record of another kind (`TARGET_WRONG_KIND`), body weight and lab results included (a latent F002/F004 hazard fixed here).
- **Old-code evidence (AC-10):** `tools/compat/old_code_check.sh <revision>` writes F007 inputs with the current code and reads them with the older revision's code in a scratch worktree. On main 48c3c94: schema-4 data refused with `RECORD_SCHEMA_NEWER` (plaintext and encrypted), F007 backups with `VAULT_INCOMPATIBLE`, a restore over them with `RESTORE_TARGET_NEWER`, no byte changed; what F007 wrote at schema 3 and the checkpoint backups open and restore. Run against the current revision the refusal checks fail, so the check tells old from new.

## D-019: Measurement time, record schema 5 and the calm clinical design (F007-S2@v0.32, 2026-11-07)

- **Time of a measurement (G-44 closed in part).** An optional "When" is parsed once, at Save, into one UTC instant with seconds 0: `YYYY-MM-DD HH:MM` or `HH:MM` (today by the injected clock) in the device's time, or a full date and time with an offset (`Z`, `+03:00`, within -12:00..+14:00). Blank means the save time. `recorded_at` is always the save time. Refusals, each on the field with its own EN/TR text: `TIME_FORMAT`, `TIME_TOO_OLD` (before 1900), `FUTURE_TIME` (more than 5 minutes ahead, the same rule as body weight), `TIME_DOES_NOT_EXIST` (the hour a clock change skipped) and `TIME_AMBIGUOUS` (the hour it repeated: an offset resolves it). The device zone sits behind an injectable `LocalZone`, so the gap, the repeat and a 30-minute shift are tested for any region. These are **entry rules only**: stored records are never re-judged (no `observed <= recorded` rule, any instant replays). A correction keeps the observation time and ignores a time typed for it; changing the time of an existing reading is G-48.
- **Record schema 5 (RS-005), additive:** `body.height` (cm), `vital.body_temperature` (°C), `vital.oxygen_saturation` (%, pulse oximeter; arterial gas values are a different measurand and are not stored), `vital.respiratory_rate` (breaths/min). No new JSON key. Each record is written at the oldest schema that holds it (weight and lab 3, slice 1 kinds 4, these 5). A new height is a new record, not a correction. SpO2 above 100 is refused at entry only (definitional, not clinical); a stored 101 loads. Units are stored as canonical strings (`°C` is UTF-8 in the log and the envelope, locked by the fixtures); no conversion, no UCUM yet (G-43).
- **Checkpoints** now also precede the first schema-5 record (4 to 5, or 3 to 5 in one step) and **never replace another backup**: a name already taken moves on by a second.
- **Weight (G-45 closed):** an ambiguous separator ("7.500", "1,234") is refused and the typed decimals are shown ("77,50" as 77.50 kg); stored weights are unchanged and still schema 3.
- **Design method (docs/DESIGN.md):** written for this project after the owner found the interface plain and cluttered. Ten principles and a twelve-item slop audit run on every screen change; one accent, hairline borders, field edges at 3:1, no colour that judges a value; Today leads with the person's numbers, entry is one sheet per kind with "More details" closed by default, a sheet is closed only by Save or Cancel, technical facts come last. No external skill was installed: an outside "unslop" skill could not be inspected from this environment and was used only as the idea of naming generic patterns and avoiding them on purpose.
- **Old-code evidence:** `tools/compat/old_code_check.sh 0617601 f007s2` (slice 1 code reads slice 2 data). Run against the current revision its refusal checks fail.

Transitive packages added: `win32` (BSD-3), `xml` (MIT), `petitparser`, `cross_file` (Flutter authors), `dbus`, `ffi`, `ffi_leak_tracker`, `args`, `plugin_platform_interface`, `flutter_web_plugins` (SDK). Lockfile committed.
- **Purpose:** the system's file dialog, so that a person can choose a raw DNA file with the mouse on Windows, macOS, Linux, Android, iOS and the web. Only `pickFile` and `clearTemporaryFiles` are used; no extension filter (a name is not trusted).
- **Isolation:** behind `GenomeFilePicker`; tests and the web smoke use a fake and need no native dialog. `release()` calls `clearTemporaryFiles` after a read because mobile choosers copy the file to a cache folder.
- **Privacy review:** the package reads the chosen file only through the OS dialog; the app keeps bytes only in session memory, parses them in an isolate on native builds (`compute`; on the web it runs on the main thread, G-54) and never writes, logs or sends them. Linux uses a desktop portal or zenity at run time; if none exists the dialog cannot open (G-55).
- **Alternatives:** pasting text (not workable for 20 MB), `dart:html`/`dart:io` directly (not portable), a path text field (not mouse-friendly).

## D-022: Genetics scope and wording (G001)

A raw DNA file is read into a list of what it contains; nothing is said about what a genotype means for the person. No-calls stay no-calls; partial calls are listed, not guessed; the genome build is shown only if the file states it. Annotation packs are plain files whose header states name, licence, build and the plus strand; a pack row quotes its source verbatim with its id, date and evidence level, and a match is only 'contains the allele the source names', 'does not match', 'not read' or 'strand cannot be told apart'. No risk wording, carrier status, copy counts or colours. SNPedia (CC BY-NC-SA) and OMIM (proprietary) are not used; ClinVar and dbSNP (NCBI), the GWAS Catalog (EMBL-EBI) are candidates for a later pack after a licence review (G-53). The bundled pack is invented and says so in every row. Genetic data is never saved in this slice (G-52).

## D-023 Appearance settings (U005, 2026-11-07)
Language, light/dark, accent colour (five tones, none red or amber, each at least 4.5:1 on its surface) and text size are display preferences, not health data. Development desktop builds keep them in `appearance.json` in the data folder (written atomically; an unreadable file is ignored and left as it is); other builds keep them in memory (G-62), so nothing is written before a vault is open. `appearance_store_io.dart` joins the native adapters allowed to import `dart:io`, reached only through the conditional export in `appearance_store.dart`. Settings open from an icon in the top bar on every screen and from Today's Tools, so a person whose device language is not Turkish can still find "Dil".

## D-024 dbSNP labels are shown, never predicted (G002, 2026-11-07)
The Genetics page reads a dbSNP Summary file the person downloads and lists the variants shared with their raw DNA file: dbSNP's alleles, consequence (missense etc.), positions and clinical significance, labelled as dbSNP's. Filters: missense only, only with a clinical label. The app says which letters the file lists (alternate or reference allele), refuses to compare indels and A/T, C/G pairs, and never predicts an effect where dbSNP gives none (owner asked; declined because an app-made pathogenicity call is a diagnosis from a value). The file is not saved.

## D-026 Phone data folder from a native channel, not path_provider (M001, 2026-11-08)
Android and iOS builds had no data folder, so a phone forgot every entry and the language choice at close (G-02, G-62). The app now asks its own native side once at start over the method channel `org.humanhealthos/paths` (Android `Context.filesDir`, iOS Application Support) and keeps `HumanHealthOS/` there; the same storage policy as desktop applies (development: labelled plaintext log in that app-private folder; staging/production: the encrypted vault, nothing written before it is created). Environment variables and portable markers are ignored on a phone. path_provider 2.1.6 was reviewed and not taken: its Android and Apple implementations pull jni, jni_flutter, objective_c and ffi with native build hooks for one folder path; about twenty lines of Kotlin and Swift do the same with no dependency. A missing or failing channel leaves the app in memory with the existing notice (fail closed). Evidence: unit tests on Linux with the phone branch forced; the native code is compiled only by the Android and iOS CI jobs; a run on a real phone is NOT_RUN.

## D-027 Display preferences of vault builds are sealed beside the vault (U018, 2026-11-08)
Staging, production and portable builds forgot language, theme and font at every start (G-62), because nothing may be written before the vault is open (D-016). Once the vault is created or unlocked, the preferences are kept in `<vault file>.prefs`, sealed with the vault's data key (ChaCha20-Poly1305, fresh nonce, associated data `hhos-vault/<version>|<vault id>|display-preferences`, distinct from every log entry). They hold no health data and are sealed anyway. They are not part of the log (no vault format change) and not part of backups. Before unlock the device language and defaults apply (the gate cannot read them). A file of another vault, a damaged one, or one that fails authentication is never used and is left as it is until a choice is changed. Choices made in the introduction before a new vault are saved when the vault is created.

## D-030 Medicines and supplements: product, plan and dose are separate records (F008, 2026-11-10)
Record schema 6 (RS-006, additive) adds `medication.item` (the product as named: name, medicine/supplement/other, ingredients, strength and form as typed), `medication.plan` (how it is meant to be taken, in the given words, with its source: prescribed, own choice or not given) and `medication.intake` (one dose taken or skipped, with an optional amount and time). Each keeps its value in kind-tagged `details`; none carries a quantity. A plan is never parsed into times or turned into doses; counts of taken and skipped doses come only from dose records; an amount is never assumed from the plan. The app holds no drug database, no dose rules and no interaction checks, and says nothing about a product. Corrections, withdrawal and deletion follow the usual history rules; a plan or a dose needs a live item. Older records and stores read unchanged; the first schema 6 record triggers the existing checkpoint backup (D-018). Medications joins the primary navigation.

## D-031 Sleep as two typed times; time in bed is not time asleep (F007-S3, 2026-11-11)
Record schema 7 (RS-007, additive) adds `sleep.night`: when the person went to bed and when they woke up (UTC instants, `details` type `sleep_night`) and, if said, how waking felt (rested, so-so, tired; null = not said, never assumed). No quantity. The time between the two is shown as "time in bed" (rule `sleep.time_in_bed` v1: waking minus going to bed), never as sleep duration or a score: the app does not know when sleep began or how often it broke. A going-to-bed time typed without a date is the last such clock time before waking, so 23:10 then 07:00 is one night; a blank waking time is now. Waking must come after going to bed and less than 24 hours later (the same clock time twice is a slip); a future time is refused; each error names the field it is about. Time zones and clock changes come from a zone the service is given, so a night across a clock change counts real time. A night can be marked entered in error or deleted on the Timeline; a typed correction is made from the Sleep card (Correct opens the night's times; a new version, the earlier one kept). The Sleep card sits on Today after the measurements; the Activity area stays planned for steps and workouts. Older stores read unchanged; the first schema 7 record triggers the existing checkpoint backup (D-018).

## D-032 How you feel: the person's own words, three optional questions (F007-S4, 2026-11-11)
Record schema 8 (RS-008, additive) adds `self.feeling_check_in` (`details` type `feeling_check_in`): energy, mood and stress, each one of three levels the person picks, each optional, at least one given; a level not picked stays not given, never "medium". The words are per question (energy: drained, steady, lively; mood: down, even, bright; stress: calm, tense, overwhelmed; Turkish: bitkin, dengeli, dinç; keyifsiz, idare eder, keyifli; sakin, gergin, çok gergin; the Turkish words avoid ones that sound clinical, such as bunalmış) so a level never reads as a lab-style high or low. Self-report, not a measurement, a score or a diagnosis: nothing is summed, averaged, trended or advised, and a stored level is never compared across questions (a low stress is calm, a low energy is drained). The card sits on Today after Sleep; both are Today sections that Settings can hide. A check-in can be withdrawn or deleted on the Timeline. Older stores read unchanged; the first schema 8 record triggers the existing checkpoint backup (D-018).
