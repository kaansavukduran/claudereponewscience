BUILD HUMAN HEALTH OS INTERACTIVE SITE / WEB APP LAB — v0.15

MISSION
Build a polished, functional, interactive web experience called a Human Health OS / Longevity ↔ Shortevity Lab from the supplied Developer Handoff.

This is the separate web-laboratory output, similar in product form to an interactive "build laboratory": users manipulate parameters and the visualized system recalculates live.

DO NOT build a static marketing landing page.
DO NOT treat this prompt as the native Android/iOS production-app build request.
DO NOT use generative AI as a required feature.
DO NOT use real user health data as default demo content.

READ FIRST
1. Read the entire supplied Master Handoff.
2. Read `107_INTERACTIVE_SITE_PROTOTYPE_AND_PUBLISHING_CONTRACT.md` as the authoritative Site-specific contract.
3. Preserve all hard invariants from the Master Handoff, especially:
   - missing != zero,
   - plan != completion,
   - self-report != diagnosis,
   - app score != validated clinical risk,
   - domain score != lifespan,
   - Shortevity score != years lost,
   - scenario != observed fact,
   - deterministic/offline core,
   - source/provenance and model-version transparency.

PRIMARY EXPERIENCE
Create an interactive scientific dashboard where a user can:
- build/configure a synthetic human profile,
- adjust body/lifestyle/health parameters,
- toggle Advanced Health Modules,
- see Longevity ↔ Shortevity outputs update live,
- compare multiple profiles/scenarios,
- inspect how each result was calculated,
- reset the demo to defaults,
- explore timeline/labs/wearable/mission/education examples.

REQUIRED MAIN SURFACES
A. PROFILE BUILDER
- age
- height
- weight
- waist/body composition where available
- blood pressure
- resting HR
- sleep duration/quality
- steps/activity/exercise
- smoking/alcohol exposure
- selected labs
- conditions
- medicines/supplements
- prevention/vaccination settings
- module toggles

B. RESULTS
Visually separate:
- Protection / Resilience
- Risk / Burden
- Function / Capacity
- Trajectory
- Coverage / Confidence
- validated-model outputs where actually implemented

Never present an arbitrary app composite as mortality probability or personalized lifespan.

C. COMPARE LAB
- add as many stored profiles/scenarios as practical
- clone profile
- modify clone without source mutation
- pin baseline
- compare selected metrics
- absolute/percentage delta only where mathematically meaningful
- reset individual scenario
- remove scenario

D. ADVANCED MODULES
At minimum demonstrate:
- Cardiovascular
- Oncology
- Metabolic/Endocrine
- Renal
- Neurology/Cognition
- Dermatology
- Musculoskeletal/Function
- Prevention
- Environment/Exposome

E. TIMELINE
Use synthetic dated events.

F. LABS
Support dated values, units, trends, missingness, provenance, and synthetic reference metadata.

G. WEARABLE DEMO
Use generated local data for sleep, steps, HR, resting HR and exercise.
Do not require a real private HealthKit/Health Connect connection for the public demo.

H. DAILY MISSIONS
Use deterministic demo rules.
Clearly distinguish planned mission from completed health/exercise event.

I. LEARN
Provide short deterministic educational cards and tiny quizzes around concepts such as healthspan, risk, biological age, reference populations, personal baselines, and correlation vs causation.

J. MODEL TRANSPARENCY
Every score/result supports `How calculated?` showing:
- result class
- inputs
- model/rule ID
- version
- missing inputs
- coverage
- limitations

DEFAULT / RESET
Include a visible `Reset Demo to Defaults` action.
Reset the synthetic demo state, not the application code or model catalog.

DEFAULT DATA
Use clearly labeled synthetic fixtures only.
Never imply synthetic demo values belong to the user.

DETERMINISM
For the same inputs + model/rule version, output must be identical.
No random health score generation.

STATE
Prefer local client state/local persistence for the public lab.
A backend is optional unless required by the selected publishing environment.
The demo must remain usable without account creation.

RESPONSIVE DESIGN
Mobile:
- stacked/card-oriented editor/results
- compact navigation
- compare profiles through horizontally scrollable/tabbed views

Desktop:
- persistent navigation
- profile controls and live results side-by-side
- wide comparison grid
- rich chart/detail panes

DESIGN QUALITY
Aim for a premium scientific control-room aesthetic.
Dense but calm.
High legibility.
No fake medical drama.
Do not encode health meaning with color alone.
Use responsive charts, tooltips/detail drawers, accessible controls and clear states.

INTERACTION QUALITY
Every visible slider/toggle/control must either:
- change a real local state/result,
- open a real settings/detail surface,
- or be intentionally disabled with explanation.

No decorative dead controls.

ACCESSIBILITY
Target WCAG 2.2 AA style compliance for the web experience:
- keyboard operation
- semantic labels
- focus states
- text scaling
- reduced motion
- chart text/table alternatives where practical
- non-color-only meaning

TESTS
At minimum test:
1. default synthetic profile loads,
2. changing weight updates applicable deterministic derived metrics,
3. source profile is unchanged when scenario clone changes,
4. reset returns demo to defined defaults,
5. missing inputs do not become zero,
6. invalid/ineligible model shows an explicit state,
7. compare works with 3+ profiles,
8. mobile and desktop layout smoke tests,
9. keyboard navigation of primary controls,
10. deterministic repeatability.

PUBLISHING / DELIVERY
If the environment supports publishing a Site, publish/prepare the project as a Site.
If not, return a normal deployable web application.
Do not fake a published URL.

Return:
- complete source tree
- exact run command
- exact production build command
- deployable build/publishable artifact
- dependency lockfile
- test results
- known limitations
- screenshots/preview only as supplemental evidence

STOP CONDITION
Do not stop at a wireframe, mockup, plan, static screenshot or prose description.
Stop when a functional interactive web lab exists in the available environment, or when a specific environment blocker is proven and every independent implementation step has been completed.
